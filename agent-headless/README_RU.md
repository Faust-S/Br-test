# IWXA Obscura Headless — автономный модуль для Personal Agent

Статус: экспериментальный публичный адаптер без GUI. Графический IWXA Browser 0.2 закрыт. Приватный Personal Agent и нормативный T2 не изменяются.

## Состав

- iwxa_obscura/controller.py: краткоживущий процесс Obscura fetch, проверка SHA256 бинарника, явных HTTPS-origin, пределы времени и байтов, временный HOME, запрет наследования секретов.
- iwxa_obscura/agent_port.py: переносимый мост к действующему PA.PORT.TOOL_PROVIDER@1.0.0. Не создаёт второй Core, ToolRuntime, политику, квитанции или хранилище.
- tests/test_controller.py: автономные негативные тесты с имитацией исполняемого движка.

В Agent уже есть ToolRuntime, ToolPolicy, ToolProviderPort и readonly web.fetch в слоте web_acquisition. После официальной регистрации локального провайдера контроллер можно связать с действующим provider_id и registry binding_digest; существующий ToolProviderPort используется как delegate для остальных операций.

Адаптер перехватывает исключительно web.fetch для точно привязанного провайдера без idempotency key, tool plan, target и других аргументов. Возвращает штатный ToolProviderResult Agent с content, content_sha256, requested_url и временной отметкой.

## Безопасность и границы доказательств

Это НЕ OS sandbox и НЕ безопасный универсальный crawler. Контроль URL применяется только к запрошенному origin; проверки перенаправлений и сетевых подресурсов ещё не обеспечены. Настоящий Obscura и Windows/Linux не проверены. Нельзя выдавать доступ к произвольным сайтам. Не передаются cookies авторизованного браузера, секреты Agent и пользовательский профиль. Дайджест защищает от случайной подмены результата, но не подтверждает истинность источника.

HTTP status и final URL не устанавливаются без доказательного наблюдения; status=200 в ответе адаптера означает успешный результат инструмента, не HTTP-код. Данные страницы недоверенные, пока отдельный маршрут U1 Evidence не проверит происхождение.

## Следующие этапы

1. Испытать настоящий закреплённый Obscura без графики на независимых сайтах и измерить RAM, время, качество извлечения.
2. Ввести контролируемый сетевой supervisor для redirects, subresources, DNS и OS sandbox.
3. Провести интеграционную проверку в существующем ToolRuntime Agent со штатной регистрацией провайдера и отрицательными проверками доступа.
4. Не вводить инструмент в обычный пользовательский маршрут до выполнения критериев безопасности.

## Hardening update 02.11.2026

Строгая канонизация HTTPS-origin (без IP, локальных/резервных зон, неканонических имен и портов кроме 443), проверка descriptor_digest в дополнение к binding_digest, проверка UTF-8 без потери байтов, elapsed_ms, скрытие консоли Windows и убийство POSIX process group при отказе. Это улучшение контроля за собственным процессом, но не OS sandbox. Тесты нужно запускать на актуальном HEAD; прохождение настоящего Obscura пока не утверждается.

## Опциональная поддержка российской и корпоративной цепочки CA (02.11.2026)

По исходникам Obscura v0.2.6 TLS-клиент поддерживает SSL_CERT_FILE / SSL_CERT_DIR. Для нестелс-сборки основной HTTP-клиент reqwest загружает дополнительные корни из SSL_CERT_FILE, а проверку TLS не отключает. В stealth-пути поведение хранилища отличается: до отдельной приёмки не включать stealth.

В агентном модуле появился PinnedCABundle: оператор явно передаёт абсолютный путь к CA PEM-бандлу, точный SHA-256 и отдельную ссылку на разрешение. Привязка CA-профиля к разрешённому HTTPS-origin происходит конфигурацией контроллера; текст страницы и web.fetch не могут менять доверенные корни.

Перед каждым запуском сертификат повторно сверяется по SHA-256, PEM проверяется через TLS-библиотеку ОС, отвергаются ключи, постороннее содержимое, ссылки и файлы с нарушенными ограничениями; затем делается временная копия, переменная SSL_CERT_FILE устанавливается только для дочернего процесса. Системное хранилище сертификатов пользователя не изменяется. Если дополнительный CA не назначен, SSL_CERT_FILE от пользователя в дочерний процесс не наследуется.

**Принципиальное ограничение:** выбор сертификатов основан на исходном origin, но внутри процесса добавленный корень доверяется всем HTTPS-подключениям, включая перенаправления и подресурсы. Это не доменная TLS-изоляция и не сетевая песочница. Пока не введён сетевой supervisor, нельзя считать этот режим безопасным для произвольных сайтов.

Корни НУЦ не добавляются в исходники; пользователь/администратор получает их на https://www.gosuslugi.ru/crt и независимо сверяет подлинность. Ссылка на разрешение в настройке не доказывает, что человек его дал: проверка полномочия остаётся у Personal Agent.

Локальный тест: `python3 -m unittest discover -s agent-headless/tests -v`. Тесты с фиктивным удостоверяющим центром не доказывают работоспособность российских сайтов, TLS ГОСТ или реального Obscura на Windows/Linux.

## Obscura Worker — наблюдение HTTP-статуса и финального адреса (02.11.2026)

Подключён **второй режим контроллера** на основе `obscura-worker` из upstream v0.2.6; это **отдельный бинарник**, не `obscura fetch`. Используется JSONL по stdin/stdout: `navigate` → `dump_text` или `dump_html` → `shutdown`. JavaScript `evaluate` не открыт агенту. В отличие от CLI, worker возвращает наблюдаемый статус главного HTML-документа (включая 404) и адрес после редиректов.

Сопоставление **конечного адреса** с разрешённым origin делается **после навигации**. Это защита от выдачи результата с чужого домена, но не предотвращает сам сетевой запрос на чужой домен. Для произвольного интернета нужен отдельный доверенный сетевой фильтр/OS sandbox на уровне всех исходящих соединений, включая DNS, redirects, JS fetch и подресурсы.

Бинарник Worker имеет свой абсолютный путь и SHA-256. Краткоживущий процесс не наследует пользовательский браузерный профиль, HTTPS_PROXY или SSL_CERT_FILE; к выбранному origin можно подключить PIN-проверенный PEM через ранее реализованный PinnedCABundle. Лимиты времени/размера применяются ко всему процессу. `networkidle2` выбран по умолчанию; для быстрых проверок Agent может явно выбрать `domcontentloaded`, но это меняет полноту наблюдения.

Объект `WorkerObservation` совместим с существующим `ObscuraAgentToolPort.invoke`, потому что предоставляет `observe(url)` и `as_data()`. Новый Core, отдельные права или схема хранения не вводятся. Результат содержит `http_status` и `final_url` **как наблюдения самого worker**, а не независимые криптографические свидетельства. Текст страницы по-прежнему недоверенный и не становится U1 Evidence автоматически.

Выполнены 14 автономных Linux/Unix-проверок JSONL на фиктивном исполняемом файле. Это не реальный Obscura и не тест независимых сайтов. Тестовый исполняемый файл использует POSIX shebang и пропускается на Windows. Реальную проверку Windows/Linux, сетевую изоляцию и достоверность DOM необходимо выполнить отдельно.


## Native origin gate для Obscura Worker (03.11.2026, кандидат)

Добавлен отдельный исходный патч `agent-headless/patches/obscura-v0.2.6-agent-origin-gate.patch`. Он рассчитан на исходники upstream `h4ckf0r0day/obscura@v0.2.6` и **не изменяет** Tauri/React или самостоятельный графический браузер. На стороне `obscura-net` проверка `validate_url` отклоняет запросы не к исходному явно разрешённому HTTPS-origin, в том числе переходы и подресурсы, которые используют этот сетевой клиент. На стороне `obscura-worker` добавлен запуск без V8 для проверки `--iwxa-attest-origin-guard` и запрет запуска без переменной `IWXA_OBSCURA_ALLOWED_ORIGIN`.

Контроллер Python `ObscuraWorkerController` по умолчанию требует именно такой pinned no-render бинарник и ожидаемый ответ build-probe *до* отправки первой навигации. Не прошедший проверку worker отвергается с `ENGINE_ORIGIN_GUARD_UNAVAILABLE`. Ключ `unsafe_allow_unpatched_worker=True` предназначен **только для изолированных тестовых подмен**, не для продукта: в результатах указывается `network_isolation=NOT_ESTABLISHED`.

### Воспроизводимая сборка кандидата

На машине с Rust toolchain и доступом к исходникам:

```sh
git clone https://github.com/h4ckf0r0day/obscura.git
cd obscura
git checkout v0.2.6
git apply --check ../Br-test/agent-headless/patches/obscura-v0.2.6-agent-origin-gate.patch
git apply ../Br-test/agent-headless/patches/obscura-v0.2.6-agent-origin-gate.patch
cargo test -p obscura-net iwxa_agent_origin_guard_tests
cargo build --release -p obscura-cli --bin obscura-worker
./target/release/obscura-worker --iwxa-attest-origin-guard
```

Схематический путь `../Br-test` необходимо заменить на фактический checkout. При сборке **не включать** feature `render`. Для Windows используются соответствующие `.exe` и PowerShell-команды проверки; это не равно уже проведённой Windows-приёмке.

**Ограничения:** Rust-сборка, тесты сетевого клиента, запуск реального Obscura и браузерное поведение на независимых сайтах не подтверждены в текущем окружении. Build-probe — признак наличия нашей версии исходников, **не удалённая криптографическая аттестация** и не ОС-песочница. Возможны другие сетевые пути внутри зависимостей и обходы, пока нет полного аудита исходящих соединений, DNS и файловых прав. Из-за ограничения origin сайты с внешними JS/CSS/CDN могут загрузиться неполностью — это ожидаемая функциональная цена строгого режима.

Системные сертификаты не меняются; опциональные CA из предыдущей итерации продолжают действовать на весь дочерний процесс, поэтому их нельзя считать строго привязанными к домену лишь за счёт этого патча.

Проверки контроллера на имитации worker: `python3 -m unittest discover -s agent-headless/tests -p 'test_origin_guard.py' -v`. Отдельные тесты `test_worker.py` включают явный небезопасный режим *только для заглушки*. После реального Rust-build нужны независимые интеграционные тесты соединений и приёмка в Agent.
