# IWXA Browser 0.2 — продуктовая программа и критерии завершения

**Статус:** утверждаемая инженерная программа следующей версии, реализация ещё не квалифицирована.
**Исходная точка:** публичная [0.1](./IWXA_BROWSER_RELEASE_0_1_RU.md), закреплённая `release/iwxa-browser-v0.1.0`.
**Разработка:** `Faust-S/Br-test@work/2026-11-01-public-browser-core`; `main` не менять.
**Цель 0.2:** быстрый, очень лёгкий, самостоятельный браузер с настоящими пользовательскими операциями IWXA T2/T3 и безопасным обращением с недоверенными сайтами. Приоритет — работающий маршрут, не количество отчётов.

## Неприкосновенные архитектурные решения

- **Один** Obscura как исполнитель страниц, **одна** Tauri-оболочка. WebView2 на Windows — только оболочка. Не добавлять Gecko/Chromium как скрытый fallback.
- **Один** существующий T2 Host/Kernel/Workspace/Result store, без копий и имитаций в браузере.
- Пользователь **явно сохраняет** Result в сайте. Напоминание об окончании работы — не автосохранение и не гарантия при сбое.
- 0.1 закреплена отдельно; код 0.2 — только в рабочей ветке; T2@main, приватный IWXA Browser, Personal Agent, Br-test@main не изменять.
- До доказанной изоляции — только точно разрешённые HTTPS-origin Learn/ArtBazi, без произвольного интернета, временных grants и небезопасных обходов.
- Существующие CI/workflow использовать по назначению; не создавать новый набор workflow/отчётов. Одновременно исправлять **один** подтверждённый продуктовый блокер.

## Последовательность практических этапов

### 0.2-A. Совместимость двигателя с настоящими SPA и управлением формами — P0

**Текущее наблюдение:** Linux live ArtBazi иногда показывает пустой `#root` после успешной загрузки HTML. В другом прогоне радиоответ не становился выбранным после нативного клика. Трёхминутный опыт завершён без доказанного решения.

**Действия:**
1. Воспроизвести в существующей bundled GUI-приёмке, сопоставить UI, факт выполнения модуля, CDP-активацию, hit-testing, React-события и планировщик.
2. Исправить конкретную первопричину в собственных публичных engine overrides или native input, а не таймаутами/обходами DOM.
3. Не допускать ложного PASS при `readyState=complete` и пустом Host; после исправления удалить диагностические обходы, которые более не нужны.

**Готово, когда:** в одном реальном запуске на чистом профиле ArtBazi штатным GUI открывает Overview, создаёт Workspace и выбирает реальные поля сервиса; тот же маршрут не требует искусственной записи IndexedDB, прямого JS-клика или ручной смены времени ожидания. Регрессии обычной навигации и IndexedDB — PASS на Windows/Linux.

### 0.2-B. Настоящий доменный Result в ArtBazi — P0

**Маршрут:** открытие реального `launch-navigator` → пользовательский выбор параметров → расчёт → передача кандидата в доменный Workspace → отдельное подтверждение сохранения → **реальная квитанция T2 Kernel** → повторное чтение именно записанного объекта → проверка тела, идентификатора и ревизии → просмотр события в истории.

**Готово, когда:** GUI-сценарий без имитаций подтверждает `event_id` от штатной команды сайта, `revision=1`, совпадение созданного и повторно прочитанного Result; после отмены завершения окна данные остаются видимыми. Без квитанции и readback — HOLD, даже если IndexedDB содержит Workspace. Никакой синтетической квитанции от браузера.

### 0.2-C. Learn, Exchange и согласованность T2/T3 — P1

**Маршрут:** аналогичное создание, явное сохранение, квитанция и чтение доменного результата в Learn → штатный экспорт `.iwxa` → проверяемый импорт через существующий T2/T3 контракт, без обхода разрешений.

**Готово, когда:** настоящие пользовательские формы и обе стороны обмена подтверждены, содержимое и редакция не подменяются; отрицательный доступ к чужой Workspace отклонён. Не разрабатывать вторую систему обмена/синхронизации.

### 0.2-D. Подтверждения и безопасность сайтов — P0 для внешнего Интернета

**Действия:**
1. Убрать опасный автоматический `true` из `window.confirm()` в используемом движке; реализовать настоящее подтверждение с отменой либо безопасный отказ до реализации.
2. Проверить закрытие окна/вкладки, смену страницы, повторный запуск и разрыв во время незавершённой работы; аварийное завершение не маскировать как безопасный выход.
3. Завершить **OS sandbox / network supervisor** для Obscura: изоляция процесса, ограничение subresources, redirects, DNS/private/loopback, CDP-токена, загрузок и файловых разрешений; тесты отказа на локальных враждебных фикстурах.
4. До прохождения этих проверок не открывать произвольный Интернет и не утверждать, что достаточно ограничения адресной строки.

**Готово, когда:** пользователь может ответить «Нет» на `confirm`; без ответа действие не выполняется; запретная сеть/редирект и выход из sandbox реально блокируются, а обычный одобренный сайт продолжает работать. Внешний Интернет остаётся HOLD до полного PASS.

### 0.2-E. Реальная лёгкость, отзывчивость и UX — P1

**Действия:** измерить одинаковые Windows/Linux сценарии у 0.1 и кандидата 0.2: холодный старт; 1 активная + 5 фоновых вкладок; 10 минут простоя; активная форма/прокрутка; возвращение к фоновой вкладке. Снимать CPU, RSS/commit, число процессов, ввод→отрисовка, время перехода и ошибки. Использовать системные показатели и воспроизводимую методику, не фантазийные сравнительные числа.

**Цели при одинаковом оборудовании и содержимом:** 0 новых независимых движков/хранилищ/оболочек; медианная память и холодный старт **не хуже** 0.1; фоновый CPU **меньше** 0.1; без потери функций и без принудительной выгрузки несохранённого результата. Если цель не достигнута — исправить регрессию, а не увеличивать число постоянных опросов.

**UX:** компактная полоса вкладок без логотипа; единый понятный индикатор реальной готовности, доступные клавиатурные действия, простые настройки с разворачиванием деталей. Режим Agent/fullscreen проектировать через существующую оболочку, не как второй исполняющий браузер.

### 0.2-F. Установка и выпуск — P1 после продуктовых P0

**Действия:** воспроизводимо упаковать один Tauri + комплектный проверенный по SHA-256 Obscura для Windows/Linux; проверить распаковку, первое открытие, разрешения, работу, закрытие и повторный запуск. Не включать диагностику/fixture mode в пользовательскую поставку; отдельного установщика для движка быть не должно.

**Готово, когда:** настоящий установленный кандидат без исходников и dev-сервера выполняет принятые сценарии, не требует секретных переменных/сертификатов для проверки домена и корректно сообщает об ограничениях. Подпись/автообновление — отдельное решение, не подменять ими сам рабочий браузер.

## Обязательный выпускной рубеж

| Рубеж | Критерий |
|---|---|
| G1. Engine/UI | Реальный ArtBazi Overview, форма, клик и расчёт PASS, а не только HTML |
| G2. T2 ArtBazi | Пользовательский Result + event_id + matching readback + ревизия PASS |
| G3. T2 Learn / Exchange | Аналогичный маршрут + перенос `.iwxa` PASS |
| G4. Data/exit | Напоминание, отмена и подтверждённый выход; без обещания несохранённой работы |
| G5. Security | `confirm` не авто-подтверждает; sandbox/сеть доказаны до снятия ограничений |
| G6. Resource | Протокол измерений Windows/Linux, сравнение с 0.1, без лишних процессов и регрессий |
| G7. Distribution | Проверенный установленный пакет Windows/Linux из единого комплектного движка |

**Правило статуса:** 0.2 не может называться «полноценным браузером для обычного Интернета», пока G5 не пройден. Можно отдельно зафиксировать ограниченный кандидат для IWXA-сайтов, но нельзя выдавать его за общую готовность.

## Техническая оценка предложений о доработках (2026-11-02)

- **Принято сейчас:** устранить отказ загрузки ES-модуля вследствие занятого диагностического состояния. Успешный HTTP-ответ и исходный код не должны превращаться в ошибку модуля из-за конфликта записи CDP Network event. Отдельно включён debug-only журнал **дочернего Obscura при обычных лимитах**, потому что журналы родительского Tauri до этого не включали события движка. Наличие этого дефекта установлено по коду; связь с пустым ArtBazi Overview требует подтверждения настоящим GUI.
- **Следующий целевой дефект:** `op_posted_task_generation()` смешивает временное `Busy` и `Gone` в значение `-1`. Простой рост числа таймерных повторов этого не решает. Нужны устойчивое поколение в контексте документа, исключение двойной доставки и отмена задач после смены документа. Исправлять после получения журнала стадии отказа.
- **Принимается с уточнением:** IndexedDB 0.1 уже фиксирует целую транзакцию до `complete` и не раскрывает повреждённый снимок как пустую базу. На 0.2 улучшить диагностику ошибок и регрессию аварийного прерывания; ограничение 64 MiB не считать целевой квотой. SQLite/WAL и миграцию со снимка внедрять **только после** доказанного профиля затрат и без второго параллельного механизма записи.
- **После ArtBazi:** заменить фиксированное `y+111` в GUI на вычисленную геометрию реальной области страницы; затем проверять события радио и клавиатуры в самом Obscura. Не подбирать координаты отдельно для каждого сайта.
- **Безопасность:** существующий синхронный `window.confirm()` с `true` без диалога нельзя квалифицировать как согласие пользователя. Promise-диалог Tauri не является прямой заменой синхронного `confirm`. До реализации настоящего подтверждения/безопасного отказа общий Интернет закрыт.
- **Отложено до замеров:** бинарный событийный Tauri Channel вместо base64/React capture, при сохранении одного читателя CDP, ограниченного числа кадров и подтверждений. Текущий опрос остаётся эталоном; PNG сохраняется до объективного сравнения CPU/RAM/задержки. Прямая передача GPU-текстуры не планируется.

## 0.2 — подтверждение действия и диагноз запуска Host (2026-11-02)

Linux GUI `#41455181460` при HEAD `12bf625`: оба ОС сохранили IndexedDB
после полного перезапуска, но ArtBazi Overview по-прежнему HOLD.
Расширенный нативный журнал показал **50 начатых и 50 завершённых**
HTTP-загрузок ES-модулей, все ответы — HTTP 200. Поэтому сетевые
тайм-ауты и повторные запросы больше не являются гипотезой по умолчанию.

не подтверждает повреждения T2/IndexedDB.

В закреплённом Obscura найдено синхронное `window.confirm() => true`
без визуального диалога — нарушение согласия для Result и удаления.
До реализации настоящего нативного пользовательского подтверждения
применён `confirm-fail-closed.patch`: `confirm()` возвращает `false`,
предупреждает в журнале и не создаёт ложное согласие. Интеграционный
Rust-тест проверяет отказ для двух разных действий и `prompt() === null`.
Эта мера не заменяет настоящий диалог: действия, требующие `confirm`,
остаются функционально HOLD. Код 0.1 и T2 не менялись.

## 0.2 — видимый отказ неподдерживаемого подтверждения (2026-11-02)

После безопасного отказа `window.confirm()` сайт может не объяснить, почему
действие не выполнено. В Tauri существующий единственный CDP-reader принимает
консольное предупреждение из активной вкладки и показывает в statusbar:
`Action not confirmed · JavaScript confirmation dialog unavailable`.
Сообщение не открывает диалог и не является разрешением. Фильтр ограничен
активной CDP-сессией, фиксированным текстом и типом события; сайт потенциально
может подделать консольный текст, поэтому он используется **только для UX**, а
не для безопасности. Уведомление сохраняется до следующего действия пользователя,
а обычная фоновая отрисовка его не стирает. Точный Rust-тест охватывает
неверную вкладку и поддельные сообщения. Настоящий нативный диалог остаётся HOLD.

## 0.2 — предельное время CDP-команды и поток событий (2026-11-02)

В нативном Tauri контроллере найден отдельный дефект: `cdp()` до этого
ждал каждое очередное сообщение с полным `command_limit`. Сайт или движок,
не отвечающий на команду, мог бесконечно удерживать управление, если в тот же
WebSocket поступали уведомления консоли, сети или кадров. Исправлено:
весь цикл отправки/получения ответа ограничен одним монотонным дедлайном;
асинхронные сообщения по-прежнему проходят через один CDP-reader, а ответ
сверяется с исходным request ID.

Добавлены два интеграционных нативных теста с локальным WebSocket peer:
непрерывные посторонние уведомления не продлевают 70ms дедлайн; настоящий
ответ после уведомления успешно принимается. Дополнительный HTTP-клиент,
процесс или стор не добавлены. Это важное ограничение зависаний, но оно
не доказывает устранения динамического import() и пустого ArtBazi Overview:
тот маршрут остаётся HOLD до реального GUI PASS.

## 0.2 — наблюдение за JavaScript task queue без изменения исполнения (2026-11-02)

Последний комплектный Linux-прогон `#41468086514` на `f08aa763`:
Windows PASS; Linux нативная оболочка, сохранение и повторное чтение
IndexedDB PASS; ArtBazi Overview и Result HOLD. По диагностическому журналу
53 начатых и 53 завершённых HTTP-модуля, два начатых графа и два завершённых
корневых загрузчика; дальнейшая инициализация Host не наблюдалась. Пока
невозможно приписывать этот отказ ни сетевому уровню, ни конкретно React
MessageChannel без измерения очереди.

Добавлена ограниченная диагностическая выборка *существующего* debug-only
`WORKSPACE_CONFIG_PROBE`: шесть численных длин приоритетных очередей
posted-task, наличие ожидающего пробуждения, признак запланированного повтора
и показания штатных счётчиков динамических DOM scripts. Запрос выполняется
только из уже существующего защищённого по origin и пути Debug probe,
не создаёт задачу, не обращается к сети, не изменяет страницу и не читает
содержимое Result. Если лексические переменные Obscura недоступны из
`Runtime.evaluate`, статус `available=false` означает отсутствие
наблюдения, а не пустую очередь. Отчёт содержит только первое/последнее
значение, максимум длины и агрегат состояния пробуждения.

Встроенный node:vm-тест проверяет, что диагностическая функция компилируется,
не изменяет очереди, различает скрытые и доступные внутренние переменные.
До нового Linux GUI-прогона причина застревания динамического импорта
остаётся неизвестной; нельзя автоматически перезагружать страницу или
расширять бюджеты ожидания.

## 0.2 — Native JavaScript window.confirm (Windows/Linux, 2026-11-02)

The real Linux ArtBazi GUI run at HEAD 39302263 mounted the T2 Overview,
created a Workspace through native clicks, and persisted its DB8 key.
Both Launch Navigator answers were selected. It then stopped at the
unimplemented synchronous window.confirm() before staging the Result.
This was a deliberate safe refusal, not a failure of HTTP/module fetching.

The packaged, owner-controlled Obscura now has the native-dialog feature:
Windows uses the OS dialog; Linux uses the GTK3 backend (no Zenity child).
The trusted engine window shows a native Yes/No request. Only OS Yes returns
true to the site. No, close, a backend failure, a missing feature, and all
