**Принципиальный вывод:** заголовок идемпотентности, который отправляет клиент, не гарантирует никакой дедупликации внутри обычного n8n workflow. Если один вызов завершился неизвестным исходом, автоматический повтор может произвести повторные реальные действия. Нельзя маркировать 2xx как доказательство отсутствия двойного эффекта; не следует пытаться «исправить» это в общих портах без отдельного продуктового кейса. На стороне IWXA использовать уже существующий статус `external_effect_state=UNKNOWN` и последующий readback результата до нового запуска. При необходимости конкретному workflow может быть задан отдельный прикладной контракт идемпотентности, но это не способность n8n по умолчанию.

## Зафиксированный первый FAIL, полезный для воспроизводимости

- Начальный серверный run: https://github.com/Faust-S/Br-test/actions/runs/41651514264 — n8n HTTP был доступен, но `POST /webhook/iwxa-public-ok` первоначально вернул 404 и действий не было; workflow ещё не зарегистрировал маршрут. Это **готовность TCP, не готовность опубликованного webhook**.
- Исправлен только публичный тестовый harness: ожидать готовности маршрута и повторять запрос **только при HTTP 404 до каких-либо внешних эффектов**. Успешный run: 2 первоначальных 404, затем HTTP 200. Это не универсальная процедура повторного исполнения операций IWXA.

## Продуктовый вывод

n8n заслуживает приоритета для расписаний и повторяемых интеграционных процессов, но **класс workflow engine не означает строгую exactly-once семантику**. В IWXA уже есть HTTP adapter, ToolRuntime и модель receipts. Отдельный следующий эксперимент — настоящий вызов через приватный `N8NWorkflowV1` и сохранение Result, не переносить приватные исходники в Br-test.

Завершённый результат — проверка published webhook, реальных HTTP побочных эффектов, сигналов 200/500, регистрационной гонки и повторных вызовов. Полной интеграции в Personal Agent, модели/ToolRuntime, Windows и восстановления после перезапуска здесь не было.
