## Почему это важно для IWXA

1. Установленный n8n может сохранять опубликованное определение workflow и восстанавливать его HTTP-вызов после полного закрытия серверного процесса.
2. Готовность порта HTTP **не равна** готовности зарегистрированного webhook; ожидание требовало соответственно четыре и два 404. Этот тестовый retry разрешён **только** до регистрации маршрута и при отсутствии побочного эффекта.
3. Старое испытание [41651901179](https://github.com/Faust-S/Br-test/actions/runs/41651901179) доказало, что два явных POST с идентичным ключом исполняют workflow повторно. Новый успешный тест рестарта **не** превращает n8n в exactly-once executor.
4. Здесь проверено *сохранение определения workflow*, но не долговременное выполнение, restart/resume прерванного workflow и не идемпотентность конечной CRM.
5. Существующий приватный `N8NWorkflowV1` не устанавливался и не выполнялся в этом run; `ToolRuntime`, `Task/Result`, receipts и UI тоже NOT_TESTED. Не объявлять уровни I3/I4 достигнутыми на основании внешнего webhook.

## Продуктовое следствие

Для повторяемых внешних процессов n8n остаётся первым интеграционным кандидатом. Штатные `ToolRuntime` и `N8NWorkflowV1` уже существуют; следующий необходимый критерий — один совместный реальный run с приватным исходником в приватной среде, затем проверка Task/Result и сохранения. Публичный тест не переносит закрытый код, не разрабатывает собственную систему разрешений и не меняет Agent 0.2.
